## 2. 问题说明与已确认的证据

v1.4.4 在从 ChatGPT 网页侧边栏切换聊天之后，可能出现：提问目录仍可显示，但点击某一提问后显示“寻找中”，随后“无法定位”；`Alt + ↑/↓` 不能将正文滚动到相应位置；插件的 `↻` 刷新也不能恢复。

### 2.1 用户实际浏览器检测

同一故障场景下，页面并非没有聊天内容：

- 实际聊天滚动容器：`clientHeight = 2946`、`scrollRange = 21551`（像素）；自身具有可见尺寸与滚动能力。
- 检测到消息锚点 12 个、可见用户消息气泡 6 个。
- 使用 v1.4.4 的 `elementHasLayout()` 判定规则：容器未通过，锚点通过 0 个，12 个锚点全部因**祖先尺寸不足**被排除；自身尺寸不足的锚点为 0。
- 用户沿真正滚动容器的祖先链向上只读检测共 25 层：第 **2、16、17、18** 层为 `display: contents`，其 `getBoundingClientRect()` 宽高为 `0 × 0`；滚动容器自身约 `495 × 2946`，其他多数祖先也具有实际尺寸。
- 浏览器还曾报告一次 JavaScript 强制重排（forced reflow，约 120 ms），仅说明需要关注重复布局读取成本，不能据此断言全部开销由扩展引起。

### 2.2 精确代码定位

`chatgpt-prompt-navigator/content.js` 当前约第 290–306 行：

```js
function elementHasLayout(element) {
  if (!element || !element.isConnected) return false;
  for (let node = element; node && node.nodeType === 1; node = node.parentElement) {
    if (node.hidden || node.inert || node.getAttribute("aria-hidden") === "true") {
      return false;
    }
    const style = getComputedStyle(node);
    if (style.display === "none" || style.visibility === "hidden" ||
        style.visibility === "collapse") {
      return false;
    }
    const rect = node.getBoundingClientRect();
    if (rect.width <= 1 || rect.height <= 1) return false;
  }
  return true;
}
```

`primaryScrollContainer()`（约第 715–768 行）先执行：

```js
const candidates = [...document.querySelectorAll(CHAT_SCROLL_SELECTOR)]
  .filter(elementHasLayout);
if (!candidates.length) return null;
```

因为 `display: contents` 元素没有自己的普通布局盒子、但其后代仍可正常显示，当前代码把正常的零尺寸包装祖先当成了“隐藏”，将真正可滚动的聊天容器排除。于是 `runNavigation()` 反复等待“活动聊天滚动区域”，最后进入“无法定位”流程。这是**已与现场证据对应的直接阻塞原因**。

**注意**：修复上述直接阻塞不等于已经证明全部跨会话导航正确。此前出现过多个滚动容器并存、用户消息锚点零高度等情况，仍需回归验证；不得把缓存或 UUID 不一致当作此次已确认的根因。

## 3. 修复目标

1. 正确处理祖先元素的 CSS `display: contents`：它虽然没有盒子，也不应据此否决有实际可见盒子的聊天滚动容器或消息锚点。
2. 保留对真正隐藏、不可操作、非活动聊天节点的防护，避免重新引入“选中隐藏旧会话”问题。
3. 用**最小修改范围**先解除 v1.4.4 已证实的容器过滤问题，不同步大改缓存、SPA 路由侦测、UUID 匹配或导航方向算法。
4. 保留 v1.4.4 的导航状态反馈（寻找中/已定位/无法定位）、有限搜索与取消机制。
5. 目标版本统一标识为 `1.4.4.1`。

## 4. 拟实施方案（以后开发时执行，不是本次变更）

### 4.1 P0：修复 `elementHasLayout()` 的判定顺序

保持 `isConnected` 以及整个祖先链上的 `hidden`、`inert`、`aria-hidden="true"`、`display: none`、`visibility: hidden/collapse` 过滤。

**关键规则：在隐藏状态检查之后，当祖先为 `display: contents` 时，跳过该祖先的矩形尺寸检查，继续检查上层祖先。** 对其他具有实际布局盒子的节点，保留现有宽高检查，避免将真正不可用节点全部放行。

拟采用的核心判断顺序示意：

```js
const style = getComputedStyle(node);
if (/* 原有隐藏状态规则命中 */) return false;
if (style.display === "contents") continue;
const rect = node.getBoundingClientRect();
if (rect.width <= 1 || rect.height <= 1) return false;
```

以上仅为逻辑示意，实施时需保留现有完整隐藏状态检查。

**边界条件**：
- `display: contents` 可能出现在目标节点自身而非仅祖先。仅跳过其尺寸检查并不保证能直接对该零盒子目标 `scrollIntoView()`：如果目标自身没有可滚动定位的盒子，应寻找属于同一用户消息、具有有效盒子的子元素，或继续渐进定位。不要把“通过校验”自动等同于“滚动成功”。
- 若祖先是 `display: none`、`visibility: hidden` 等真实隐藏状态，仍然拒绝。
- 不要删掉整条祖先链检测，也不要对所有零尺寸元素无条件放行。
- 不要将 `display: contents` 错误当作可测量尺寸的实体布局容器。

### 4.2 P0：保持活动滚动容器筛选

- `primaryScrollContainer()` 保留枚举、候选活动性校验和多容器场景判断；不要退回 `document.querySelector(CHAT_SCROLL_SELECTOR)` 只取第一项的旧实现。
- 首先应让实际滚动容器不再因 `display: contents` 祖先被过滤；之后验证它与当前聊天的关联、实际尺寸和滚动范围。
- 不能仅因候选消息 ID 数量较多就选中隐藏旧会话；尤其当页面含多个滚动容器时，要核验选中对象确实属于活动会话。
- 若修复 `elementHasLayout()` 后仍存在多个同等候选，必须查明活动视图依据，不能随意选择 DOM 第一个或最后一个。

### 4.3 P1：锚点定位与性能回归（先验证，必要时再补最小修复）

- 复查 `currentMountedPromptEntries()`、`resolvePromptElement()`、`scrollElementIntoView()` 对新规则的实际表现。
- 统计“可见气泡数量 / API 消息 ID 匹配数 / 可用定位锚点数”；这些量分别记录，不得相互替代。
- 当消息包装节点属于 `display: contents` 或无布局盒子时，必要时利用同一用户消息下的实际可见子元素定位，避免误用隐藏旧会话节点。
- 检查频繁遍历祖先并读取 `getComputedStyle()`、`getBoundingClientRect()` 的成本，必要时只在同一次导航/布局周期进行合理的结果复用，不缓存跨 SPA 会话的陈旧 DOM 判定。
- 如果 P0 修复后导航仍有问题，应先记录具体失败路径（容器无效、UUID 未匹配、目标无盒子、滚动到位失败等），再单独做最小补丁，不在本轮凭猜测修改所有算法。

## 5. 验证策略与验收标准

### 5.1 无写入的修复前后规则对照

在同一个出错会话上，用只读 Console 脚本比较现有规则和“跳过 `display: contents` 尺寸检查”后的规则，分别统计：
- 当前聊天容器的可用性判断是否从 false 变为 true；
- 12 个原先被排除的锚点中，有多少在新规则下通过；
- 是否仍存在真正隐藏或无布局目标被错误接受。

这一对照是实施前基线，不能因为 `fixedContainerValid = true` 就直接宣布所有导航已修复。

### 5.2 功能回归检查表

- [ ] 失败场景中，实际滚动容器在修复后通过有效性检查，`primaryScrollContainer()` 返回正确的活动容器。
- [ ] 祖先有 `display: contents`、但实际消息显示正常时，不再被无条件否决。
- [ ] 真正的 `display: none` / `visibility: hidden` / `hidden` / `inert` / `aria-hidden` 节点仍被拒绝。
- [ ] 点击当前屏幕可见的用户问题，能实际定位到对应内容，不只是更新目录高亮。
- [ ] 长对话从最新消息跳往最早、中间提问，再从历史提问返回最新提问，导航准确。
- [ ] 不刷新网页，连续从会话 A → B → C → A，分别点击目录项、使用 `Alt + ↑/↓` 和 `Alt + Home/End`，正文与目录一致。
- [ ] 页面同时存在多个 `.thread-scroll-container`（包括无尺寸旧会话容器）时，选中活动聊天容器，不误滚其他会话。
- [ ] 在正常 `column` 和 `column-reverse` 滚动布局中分别验证顶部、中部、底部。
- [ ] 暂时 `当前0/N` 时，允许受控寻找；定位失败应有正确原因，不能将错误容器当作成功。
- [ ] 插件 `↻`、侧边栏 `Alt + Q`、搜索过滤、手动滚轮取消导航等既有功能不退化。
- [ ] 不造成明显滚动卡顿、布局抖动、无限循环或高频 API 请求。
- [ ] 验证 Chrome 与 Edge；对于无法在本环境真实测试的行为，明确标注“待浏览器验收”，不得声称通过。

### 5.3 建议的最小自动化测试用例

1. 祖先包含 `display: contents`，滚动容器自身尺寸有效：应通过布局可用性判断。
2. 祖先存在 `display: none` 或 `hidden`：应拒绝。
3. 祖先存在真实零尺寸布局盒子：应按规则拒绝。
4. 目标节点自身为 `display: contents`：只有在找到真实可定位的目标子元素并验收到位时才可报告成功。
5. 多候选容器：一个隐藏无滚动、一个活动可滚动，应选中后者。
6. SPA 切换后容器引用改变：应重新解析，不复用旧会话 DOM。
